# 医院知识库维护

先建陪诊服务知识即可：地点、楼层、报到/缴费/取药流程、开放时间、设施及服务边界。不需要以大型疾病问答库作为启动条件。

## 事实来源

虚拟环境的事实来自人工定义的 `seeds/hospital.json`；每个条目都标记虚构来源。LLM 不负责创造或更新这些事实。真实部署时，应替换成经医院核实的信息并填写来源、核实日期及可选失效日期。

`places` 的 ID 是稳定工具参数，不随名称变化；`edges` 引用这些 ID。流程与患者预约科室也必须引用现有地点。当前程序验证引用和条目格式，并通过测试验证路网连通和每个患者流程可完成。

`documents` 示例：

```json
{
  "id": "service:checkin",
  "title": "预约后的报到",
  "text": "本虚拟医院：已预约患者前往对应候诊区报到，留意叫号。",
  "keywords": ["预约", "报到", "挂好号"],
  "source": "Synthetic Hospital v1：虚构种子",
  "reviewed_at": "2026-10-21",
  "expires_on": "2027-10-21"
}
```

日期示例表示字段格式，不代表真实医院审核。未填写开放时间时，系统应说不知道，不让模型推测。临床诊断、用药和检查准备建议不在当前知识范围内。

## 测试数据隔离

`scenarios/seed_dialogues.json` 与 `scenarios/multi_turn.json` 是测试种子。扩写器保留患者 ID、预期动作、步骤结构和模拟事件，只改写自然语言槽位。生成结果不能加载为知识库。

结构校验不能发现全部语义漂移，例如把“询问位置”改成“请求带路”。因此生成结果标记待人工复核。不要用同一个生成模型的自评分替代人工检查。

检索先用可解释的本地关键词方案。积累真实问题和失败案例后，再决定是否增加向量检索、重排序或文档导入。
